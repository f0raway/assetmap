# assetmap 优化改进方案

本文档梳理了 assetmap 项目的优化方向，按优先级排序，供后续开发参考。

---

## 一、TUI 配置向导（高优先级）

### 1.1 背景

当前配置方式是通过编辑 `config.yaml` 文件，存在以下问题：
- 100 行 YAML 对新手不友好
- 需要记住字段名和格式
- 填错了要运行后才知道
- 高级参数和必填项混在一起
- 密钥直接显示在终端

### 1.2 方案

新增 `assetmap configure` 命令，提供交互式配置向导。

#### 技术选型

推荐使用 `questionary` 库：
- 轻量，基于 prompt_toolkit
- 支持密码输入（不回显）
- 支持选择、确认、文本输入
- 零学习成本，API 简单

#### 辅助命令

```bash
assetmap configure              # TUI 向导，配置核心项
assetmap configure --advanced   # 打开 config.yaml 编辑高级选项
assetmap configure --show       # 显示当前配置（脱敏）
assetmap configure --reset      # 重置为默认配置
```

## 二、手动资产补充 TUI（高优先级）

### 2.1 背景

当前手动资产补充通过编辑 YAML 文件完成，存在以下问题：
- 需要理解 YAML 语法
- 字段多，格式复杂
- 需要按单位组织数据
- 对新手不友好

### 2.2 方案

新增 `assetmap add-asset <task_id>` 命令，提供交互式资产添加。

#### 交互设计

```bash
assetmap add-asset <task_id>
```

| `assetmap asset-gap-template` | 导出缺口让其他人帮忙补 | 生成待填模板 |

## 三、流程改进：discover 后交互检查点（高优先级）

### 3.1 背景

手动资产补充应该发生在 discover 阶段之后，此时公司树已经建立，归属单位选择自然成立。

### 3.2 方案

在 discover 完成后增加交互检查点，询问是否手动补充资产。

#### 流程调整

```
discover（采集公司树）
    ↓
展示发现结果，询问是否手动补充 ← 新增交互点
    ↓
用户选择补充 → TUI 逐条添加 / 文件导入
用户选择跳过 → 继续
    ↓
subdomains → port-scan → classify → url-discover → report → deliver
```

#### 交互界面

```
[scan] 1/3 discover enterprise tree and filing assets
[scan] discovered task=1, companies=15, assets=42

┌──────────────────────────────────────────────────┐
│  企业资产采集完成                                  │
├──────────────────────────────────────────────────┤
│                                                  │
│  目标: 苏州市能源发展集团有限公司                   │
│  发现公司: 15 家                                  │
│  发现域名: 8 个                                   │
│  发现资产: 42 条                                  │
│                                                  │
│  主要公司:                                        │
│  ● 苏州市能源发展集团有限公司 (母公司)              │
│    域名: energy.cn, energy.com.cn                │
│  ● 苏州市能源投资有限公司 (子公司, 100%)           │
│    域名: -                                       │
│  ● 苏州市能源电力有限公司 (子公司, 51%)            │
│    域名: power-energy.cn                         │
│  ... 还有 12 家                                  │
│                                                  │
│  ? 是否手动补充资产?                              │
│    ● 跳过，继续自动流程                            │
│    ○ 逐条添加资产                                 │
│    ○ 从文件批量导入                               │
```

#### 命令行参数

```bash
# 默认行为：交互询问
assetmap scan "公司名称"

# 跳过询问，直接继续
assetmap scan "公司名称" --no-manual-prompt

# 跳过询问，直接进入 TUI 补充
assetmap scan "公司名称" --manual-add

# 跳过询问，直接导入文件
assetmap scan "公司名称" --manual-file data/manual_assets.yaml
```

## 四、增量积累机制（中优先级）

### 4.1 背景

当前对同名公司重复扫描时，是"断点续跑"模式。但用户希望资产数据只会增量，不会减少，每次扫描都在上一次基础上补充。

### 4.2 方案

对同名公司扫描时，新任务继承历史任务的数据，增量扫描，全量报告。

#### 行为对比

**当前行为**：
```
第1次 scan "苏州能源" → task_001，发现 10 个域名
第2次 scan "苏州能源" → 复用 task_001，断点续跑
```

**改进后**：
```
第1次 scan "苏州能源" → task_001，发现 10 个域名
第2次 scan "苏州能源" → task_002，继承 task_001 的数据，增量扫描
  - 已有 10 个域名 + 新发现 3 个域名 = 13 个域名
  - 历史数据不丢失，只增不减
```

#### 实现思路

```python
# 查找同名目标的历史任务
previous_tasks = session.exec(
    select(ScanTask).where(
        ScanTask.target == target,
        ScanTask.status == "completed",
    ).order_by(ScanTask.finished_at.desc())
).all()

if previous_tasks:
    latest = previous_tasks[0]
    # 新任务继承历史资产
    # 1. 复制公司树（Company + CompanyEdge）
    # 2. 继承已有的 InternetAsset 关联
    # 3. 继承已有的 SubdomainRecord、DnsRecord 等
    # 4. 后续阶段只处理增量部分
```

#### 增量体现

- **子域名枚举**：已有的子域名跳过，只枚举新的
- **端口扫描**：已有的 IP 跳过（或只扫新增端口）
- **URL 识别**：已有的 URL 跳过
- **报告**：基于全量数据生成，不丢失历史

#### 用户体验

```
[scan] 检测到历史任务 task_001 (2024-01-15 完成)
[scan] 继承历史数据: 10 域名, 25 IP, 8 Web 入口
[scan] discover 完成, 新增 3 个域名
[scan] 当前全量: 13 域名, 25 IP, 8 Web 入口
[scan] 继续子域名枚举（仅新增域名）...
```

#### 命令行参数

```bash
# 默认行为：继承历史数据，增量扫描
assetmap scan "苏州能源"

# 完全重置，忽略历史数据
assetmap scan "苏州能源" --refresh
```

## 五、配置策略（已满足）

### 5.1 当前设计

密钥直接写在 `config.yaml` 文件中，这是默认行为，已经满足便捷性需求。

### 5.2 配置优先级

```
环境变量 > config.yaml > 默认值
```

- **日常使用**：直接读 config.yaml，方便
- **特殊场景**：环境变量临时覆盖，灵活

### 5.3 安全保障

- `.gitignore` 已经排除 `config.yaml`
- 项目是本地工具，不会部署到公共服务器
- 文件权限可以限制（`chmod 600 config.yaml`）

## 六、架构优化（低优先级）

### 6.1 CLI 文件拆分

当前 `cli.py` 有 1189 行，所有命令都在一个文件里。建议按功能域拆分：

```
assetmap/
├── cli/
│   ├── __init__.py
│   ├── pipeline.py    # scan, discover, run, status
│   ├── report.py      # report, deliver, quality-check
│   ├── assets.py      # import-assets, asset-template, asset-gap-template, add-asset
│   ├── config.py      # init, env-check, ai-check, configure
│   └── review.py      # review-workorder, import-review, improve
```

### 6.2 配置验证统一

将配置验证逻辑统一到 `config.py`，`environment.py` 只负责环境检查。

## 七、实施建议

### 优先级排序

| 优先级 | 改进项 | 工作量 | 价值 |
|-------|--------|-------|------|
| 高 | TUI 配置向导 | 中 | 大幅降低新手门槛 |
| 高 | 手动资产补充 TUI | 中 | 提升使用体验 |
| 高 | discover 后交互检查点 | 小 | 流程更自然 |
| 中 | 增量积累机制 | 大 | 数据更有价值 |
| 低 | CLI 文件拆分 | 中 | 维护性优化 |

### 实施顺序

1. **第一阶段**：TUI 配置向导 + discover 后交互检查点
   - 新增 `assetmap configure` 命令
   - 在 scan 流程中增加交互检查点
   - 引入 `questionary` 库

2. **第二阶段**：手动资产补充 TUI
   - 新增 `assetmap add-asset` 命令
   - 支持逐条添加、按单位补充

3. **第三阶段**：增量积累机制
   - 调整 ScanTask 复用逻辑
   - 实现历史数据继承
   - 增量扫描，全量报告

4. **第四阶段**：架构优化
   - CLI 文件拆分
   - 配置验证统一
